# M2Y 项目路线总控设计

## 1. Task model

本任务是长期父任务，负责“测量、排序、集成验收”，五个子任务负责实际产品交付。父任务的百分比只由子任务验收证据驱动，不能由父任务文档本身驱动。

```text
本地安全与 libsignal Spike（已完成）
  → 生产身份 / 配对 / 安全号码
  → 密文同步 / 离线 / 冲突
  → Chat 富消息 / 文件生命周期
  → Space 完整对象 / Activity / 时间线 / 搜索
  → 设置 / 恢复 / 设备 / iOS / 发布门禁
  → 最终双设备与 Figma/PRD 集成验收
```

## 2. Progress contract

每次更新必须同时包含：

1. 子任务状态：`planning`、`in_progress`、`completed` 或明确阻塞原因。
2. 用户可观察成果：可在什么设备、什么入口完成什么动作。
3. 技术证据：自动化门禁、模拟器/真机、双设备或服务端不可解密证据。
4. 声明边界：仍不能对用户承诺的能力。
5. 权重变化：只更新被证据覆盖的能力域得分，并保留旧值与原因。

完成度公式固定为：

`完整 P0 完成度 = 六个能力域当前得分之和 / 100`

如果权重本身需要调整，必须记录为产品范围变更，说明新旧算法下的数值，不能静默改写历史。

## 3. Child ownership

| Child | Owns | Does not own |
|---|---|---|
| Identity/Pairing | 身份密钥、M2Y-ID、配对、安全号码、身份变化 | 通用消息同步、完整设置与设备恢复 |
| Sync | transport、outbox/inbox、幂等、离线重试、冲突底座 | 富消息 UI、文件产品体验 |
| Rich Chat/File | 图片/文件/引用/状态/失败恢复、附件密钥与缓存清理 | Activity、全局搜索和设置子页 |
| Space surfaces | 五类 Item、Activity、时间视图、搜索、对象状态 | 身份协议和发布合规 |
| Security/Release | PIN/恢复、设备撤销、隐私控制、iOS、AGPL/发布 | 重做前四项已验收的业务规则 |

## 4. Integration gates

- 身份/配对完成前，不允许真实关系 UI 宣称已建立 E2EE。
- 同步完成前，Chat/Space 仍不得展示“已送达另一端”“已同步”等状态。
- 附件产品化必须验证正文不通过 JS/native bridge 冒充流式文件加密。
- iOS 不继承 Android 验收结论；必须有独立原生构建、存储和生物识别证据。
- 最终验收必须以两台真实设备或等价的可审计双端环境覆盖端到端流程。

## 5. Operational update

子任务归档后，在父任务 `research/progress-snapshots.md` 追加一条快照，再更新 `prd.md` 当前基线。快照至少包含日期、子任务、旧分数、新分数、证据路径和仍开放的阻断项。

若子任务 no-go：保留得分不变，记录替代方案和对后续依赖的影响；不得为了维持时间表而降低安全门禁。
