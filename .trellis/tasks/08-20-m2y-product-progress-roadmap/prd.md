# M2Y 项目完成度与产品路线总控

## Goal

建立一份可持续维护的项目总控记录，把“阶段任务完成”和“完整产品完成”明确分开；以当前代码、Figma/PRD 差距报告和已归档验收任务为基线，通过五个可独立验收的子任务推进 Android 优先的完整 P0 产品。

该任务的价值不是制造一个看似精确的百分比，而是让每个完成度变化都能追溯到用户可观察能力、自动化门禁和真机证据。

## Background

- Figma 文件约含 50 个移动端画面与规格材料，其中包括真实页面、弹窗、状态变体、流程图和状态表，不能按“一个画面一个路由”统计。
- 已完成并归档三个阶段任务：Figma 基础交互 MVP、Android 安全与数据基础、Android E2EE 原生技术验证。
- 当前真实产品页面集中在 Chat、Space、Shared Item Detail、Settings；身份、配对和安全号码路由仍是占位边界，E2EE 仅有开发验收 harness，生产同步尚未实现。
- 现有《M2Y 设计稿与 PRD 差距及修改方案》记录了 64 个设计/需求差距项；这些差距项不是 64 个独立页面，但证明完整 P0 仍有大量用户流程和状态未覆盖。
- 已确认的产品决策：Android 优先；接受 libsignal 的 AGPLv3 开源义务；执行顺序为本地安全基础 → 生产身份/配对/E2EE → 密文同步 → 丰富业务页面与发布准备。

## Requirements

### R1 — 统一完成度口径

- 始终分别报告阶段任务、M0 技术路线、完整 P0 产品和发布准备四种口径。
- 开发验收页、模拟数据、native Spike 和占位路由不得计为已上线产品能力。
- 百分比只允许基于固定能力权重和可验证证据更新，不得因新增代码行数或 Figma frame 数量直接增加。
- 新证据与当前口径冲突时，先修正文档和基线，再继续下一里程碑。

### R2 — 父子任务治理

- 本任务作为父级总控任务，维护基线、依赖顺序、子任务状态、跨任务风险和最终集成验收。
- 五个子任务分别拥有自己的 PRD、设计、实施计划、测试、真机证据和归档记录；不把多个独立里程碑混入一次提交。
- 子任务必须按依赖顺序启动；若后续研究证明可安全并行，必须先在父任务记录依赖变化与理由。
- 父任务不以“所有文档已创建”为完成条件，只有全部子任务和最终集成验收通过后才能归档。

### R3 — 每次里程碑后的进度更新

- 每个子任务归档后，更新本 PRD 的完成度表、对应得分、证据链接和剩余风险。
- 更新记录必须说明“新增了什么用户可观察能力”“哪些安全/同步声明现在成立”“仍然禁止声明什么”。
- 如果子任务只完成技术 Spike，不增加或仅部分增加产品完成度，并明确原因。
- 保留历史基线快照到 `research/`，避免反复覆盖后无法解释百分比变化。

### R4 — 执行顺序与里程碑

1. `08-20-android-production-identity-pairing`：真实 M2Y-ID、配对请求、安全号码和 libsignal 生产边界。
2. `08-20-ciphertext-sync-foundation`：服务端不可解密的 transport、outbox/inbox、离线重试和冲突基础。
3. `08-20-rich-chat-file-lifecycle`：富消息、发送状态、失败恢复、附件加密和文件生命周期。
4. `08-20-space-extended-product-surfaces`：五类 Shared Item、Activity、时间视图、搜索及完整状态。
5. `08-20-security-settings-release-readiness`：设置子页、恢复换机、设备撤销、隐私、iOS 和发布门禁。

### R5 — 项目边界

- Android 继续作为首个实现与验收平台，但不得把 Android 结论冒充 iOS 或双平台完成。
- 不在 JavaScript/TypeScript 中实现占位密码学，不把未审计的 Spike 表述为生产安全认证。
- 服务端目标是零明文、不可解密，不承诺零服务端留存。
- Figma 对齐必须服务于真实状态和交互；不得为了提高页面数量而创建无法工作的装饰页面。

- [x] 五个独立子任务已创建并关联到父任务。
- [x] 子任务依赖顺序、范围边界和父任务更新规则已记录。
- [ ] 生产身份、配对与安全号码子任务通过验收并归档。
- [ ] 密文同步与离线冲突子任务通过验收并归档。
- [ ] Chat 富消息与文件生命周期子任务通过验收并归档。
- [ ] Space 完整对象与辅助页面子任务通过验收并归档。
- [ ] 安全设置、设备恢复与发布准备子任务通过验收并归档。
- [ ] 完成 Android 端到端双设备集成验收，覆盖首次使用、配对、消息、文件、Space、重启、离线恢复和安全号码变化。
- [ ] 完成 Figma/PRD P0 差距复核，所有阻断项关闭或由用户明确降级/延期。
- [ ] README、第三方许可证、发布说明和完成度基线与最终实现一致。

## Out of Scope

- 在本父任务规划阶段直接实现产品代码。
- 把 P1/P2 需求自动提升为 P0；新增需求需要单独记录范围和对完成度口径的影响。
- 用未连接的静态页面替代真实身份、加密、同步、文件或恢复能力。

## Key Decisions

| Decision | Choice | Consequence |
|---|---|---|
| 进度统计 | 能力权重 + 验收证据 | 不按页面数、代码行数或提交数制造虚高进度 |
| 任务结构 | 一个父级总控任务 + 五个可验收子任务 | 保持整体视图，同时避免跨里程碑混改 |
| 平台顺序 | Android first | iOS 单独验收，不阻塞 Android 前四个里程碑的学习 |
| 安全顺序 | 身份/配对 → 同步 → 丰富页面 | UI 只展示已经存在且可验证的协议与状态 |
| 当前产品基线 | 33% | 每个子任务归档后按相同权重重新评分 |
