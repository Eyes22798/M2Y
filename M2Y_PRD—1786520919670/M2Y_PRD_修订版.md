## 0. 本次修订摘要

本版不是对原 PRD 的局部增补，而是一次产品结构重构：

- 将 M2Y 从“只有两个人的聊天 App”重新定义为“**两个人的私密协作空间，聊天是入口**”。
- 将共享空间从待办、笔记、文件、决策、日历五个独立工具，重构为“**Space Home + Shared Item（共享项）**”。
- 建立 `Chat → Save to Space → 协作 → 状态回到 Chat` 的核心闭环。
- 新增收藏项（Pin）、置顶、Waiting 状态、Activity 与统一搜索。
- 将 Decision 改为 Agreement（约定），以“双方确认同一内容版本”为核心，不在 MVP 中承诺法律存证能力。
- 将“文件仓”改为聊天文件的自动索引视图，不要求用户重复上传，也不在 MVP 中建设独立云盘。
- MVP 不做实时 CRDT、协同光标、看板、完整日历、重型 Markdown 工作台、可信时间戳等高复杂度能力。
- 将“零服务端留存”统一修正为“**服务端零明文，产品方不可解密**”，同时明确必要密文与最小化运行元数据的存在。
- 将北极星指标从“多聊天”改为“双方围绕同一共享项发生有效协作”。

## 1. 产品概述

### 1.1 产品定位

M2Y 是一个**只属于两个人的私密协作空间**。

它不构建社交网络，不做群聊、通讯录、内容推荐或情侣化包装。每个 M2Y 关系中只有两个人：他们在 Chat 中交流，在 Space 中共同保留、推进和确认重要信息。

> **聊天是入口，Space 是两个人的长期共享上下文。**

### 1.2 一句话定义

> **M2Y：只有你和另一个人的聊天与共享空间。消息会过去，重要的事留在你们之间。**

### 1.3 用户问题

现有聊天工具善于承载即时交流，但不善于维护两个人之间的长期状态：

- 一件待处理的事被后续消息淹没。
- 双方说过的结论缺少清晰、共同确认的版本。
- 地址、链接、截图和文件“发过但找不到”。
- 对方是否已处理、是否正在等待自己，缺少轻量可见性。
- 用户被迫在聊天、待办、笔记、网盘、日历之间反复搬运信息。
- 敏感关系既需要协作与跨设备同步，又不希望平台读取内容。

M2Y 的解决方式不是把五个完整工具塞进聊天 App，而是让聊天中的内容低成本成为双方共同拥有、可继续行动的共享项。

### 1.4 产品心智

```text
Talk → Save → Act → Remember

Talk      两个人自然聊天
Save      把值得保留的内容保存到 Space
Act       分工、编辑、等待、确认或完成
Remember  形成可查找的共同上下文
```

### 1.5 核心价值

| 价值 | 产品表达 |
|---|---|
| 关系唯一 | 全局只服务一对固定关系，无聊天列表与社交噪音 |
| 对话可沉淀 | 单条或多条消息可统一“保存到 Space” |
| 双人协作 | 围绕负责人、Waiting、双方确认设计，而非照搬多人项目管理 |
| 上下文连续 | Chat 与 Shared Item 双向跳转，执行结果回到 Chat |
| 服务端不可读 | 内容端到端加密；服务端保存必要密文，但不持有内容解密密钥 |
| 低身份暴露 | 使用 M2Y-ID 建立联系，不强制手机号、邮箱或通讯录 |

### 1.6 目标用户与场景

| 关系类型 | 典型协作 | M2Y 的核心价值 |
|---|---|---|
| 工作搭档 / 创业双人组 | 分工、文件、结论确认、时间协调 | 对话直接转为双方可执行的状态 |
| 顾问与客户 / 专业服务双方 | 材料、行动项、阶段约定 | 私密、清晰、可回看，不依赖多个工具 |
| 家人 / 照护二人组 | 用药、预约、地址、证件与提醒 | 一眼知道“什么需要我处理” |
| 师徒 / 教练与学员 | 任务、反馈、阶段目标 | 持续的双人上下文与责任闭环 |
| 研究者 / 记者与信源 | 匿名沟通、临时敏感信息 | 降低身份关联并提供可选焚毁模式 |
| 朋友 / 长期协作伙伴 | 行程、共同采购、重要信息收藏 | 不要求关系是情侣，也不需要项目管理知识 |

### 1.7 产品边界

M2Y 在 MVP 中明确不做：

- 群聊、好友列表、动态、推荐流、公开主页。
- 情侣签到、纪念日包装、亲密度排名等关系预设。
- 多人项目管理、团队权限、Sprint、看板和复杂工作流。
- 完整文档套件、实时多人光标、数据库式笔记。
- 独立网盘、文件夹树和大容量云存储套餐。
- 完整月历/周历、外部日历双向同步。
- 法律意义上的电子签名、可信时间戳或证据保全承诺。
- 云端读取消息内容的 AI 功能。

### 1.8 产品原则

1. **两个人优先**：所有状态与动作都以“我、对方、双方”表达。
2. **Chat 是入口**：不要求用户先分类再表达，先聊天，之后再沉淀。
3. **Space 是状态，不是工具集合**：首页按“需要处理什么”组织，类型只作为筛选。
4. **一次保存，保留来源**：保存后可回到原始聊天，避免复制后失去语境。
5. **用 Chat 讨论，不复制评论系统**：Shared Item 不另建评论区。
6. **双向有效才算成功**：单方面创建大量内容不等于协作成立。
7. **隐私承诺必须可实现**：不使用“零元数据”“绝对防截屏”“远程必然擦除”等不可验证表述。
8. **先验证频率，再增加复杂度**：CRDT、看板、完整日历等由真实行为数据驱动。

## 2. 产品模型与功能架构

### 2.1 核心产品模型

```text
M2Y Pair（唯一双人关系）
│
├── Chat：流动信息
│   ├── 发送与讨论
│   ├── 常规 / 阅后即焚
│   └── 保存到 Space
│
└── Space：长期共享状态
    ├── Space Home
    │   ├── 需要你
    │   ├── 接下来
    │   ├── 置顶
    │   └── 最近更新
    ├── Shared Item
    │   ├── Pin / 收藏项
    │   ├── Task / 待办
    │   ├── Note / 笔记
    │   ├── File / 文件
    │   └── Agreement / 约定
    ├── Activity
    ├── 时间视图
    └── 统一搜索
```

### 2.2 Chat ↔ Space 核心闭环

```text
聊天产生重要信息
        ↓
统一“保存到 Space”
        ↓
成为 Pin / Task / Note / Agreement
或聊天文件自动成为 File
        ↓
双方执行、编辑、等待、确认
        ↓
关键状态以卡片/系统事件回到 Chat
        ↓
继续讨论；讨论消息再次关联 Shared Item
```

### 2.3 为什么采用 Shared Item

所有沉淀内容共享一组基础能力：

- 有创建者、更新时间和生命周期。
- 可置顶、归档、删除和搜索。
- 可关联一条或多条原始聊天消息。
- 可从 Item 跳回 Chat，也可在 Chat 中发起对 Item 的讨论。
- 可出现在 Space Home、时间视图和 Activity 中。
- 内容整体端到端加密，服务端只同步密文信封。

类型差异由各自负载和状态扩展表达，不再建设五套彼此割裂的列表与导航。

### 2.4 功能架构

```text
M2Y
│
├── 0. 关系层
│   ├── M2Y-ID 与本地显示名
│   ├── 双人配对与安全号码验证
│   ├── 设备授权与撤销
│   └── 解绑、保留只读或删除本地数据
│
├── 1. Chat
│   ├── 文本 / 图片 / 文件 / 引用 / 撤回
│   ├── 语音 / 位置（P1）
│   ├── 常规 / 阅后即焚模式
│   └── 保存到 Space / 讨论 Shared Item
│
├── 2. Space
│   ├── Space Home
│   ├── Shared Item
│   ├── Activity
│   ├── 时间视图
│   └── 本地统一搜索
│
├── 3. 隐私与控制
│   ├── 端到端加密与本地安全存储
│   ├── 应用锁 / 后台遮罩 / 缓存管理
│   ├── 截屏与录屏风险提示 / 水印
│   ├── 诱饵界面（P1）
│   └── 本地安全记录
│
└── 4. 系统层
    ├── 密文同步与离线投递
    ├── 多设备授权
    ├── 通知与本地提醒
    ├── 加密导出
    └── 关系解除与删除请求
```

## 3. 核心功能需求

### 3.1 关系层：唯一双人关系

#### 3.1.1 M2Y-ID 与注册

- 首次启动在设备端生成身份密钥与随机 `M2Y-ID`，格式示例：`m2y-7Q4K-X9A2`。
- 不强制采集手机号、邮箱、通讯录或真实姓名。
- 显示名和头像可选，仅对本人及配对对象可见；头像作为加密内容同步。
- 注册页必须说明：M2Y-ID 降低账户与现实身份的直接关联，但不能单独承诺网络层“完全匿名”。
- 提供一次性恢复码/恢复包；平台无法替用户恢复端到端加密内容。

#### 3.1.2 配对

支持：

1. 扫码配对。
2. 输入 M2Y-ID 发起请求。
3. 输入 10 分钟有效的一次性握手码。

规则：

- 配对请求必须由双方设备确认。
- 配对时展示安全号码/公钥指纹，支持当面或其他可信通道比对。
- 配对成功后全局只有该关系，不展示聊天列表。
- 更换对象前必须解除当前关系，并明确选择本地数据处理方式。
- 服务端可持有路由与反滥用所需的最小化标识，但不得持有关系内容或内容解密密钥。

#### 3.1.3 设备授权

- 设备模型按单个身份最多 5 台设计；MVP 先支持 1 台活跃移动设备及受控换机，P1 再开放多台设备同时在线。
- 换机或新增设备默认必须由一台已授权设备扫码或确认；若原设备不可用，则使用恢复材料并触发清晰的安全号码变化提示。
- 移除设备后，停止向该设备发放新的会话密钥与密文更新。
- 无法保证已被越狱、Root、离线复制或由用户自行导出的旧明文被远程抹除；产品必须在操作前说明此限制。

#### 3.1.4 解绑

解绑发起方可选择：

- **删除本机数据**：销毁本机密钥和本地数据库。
- **保留只读副本**：本机保留当前可解密内容，不再同步。

解绑后：

- 双方不再发送新消息或共享项更新。
- 服务端删除未投递密文并按数据保留策略删除配对路由。
- 对端收到解绑通知后执行其本地策略；“远程删除”仅为尽力而为，不作绝对保证。

#### 3.1.5 验收标准

- [ ] 不提供手机号和邮箱也可完成注册、配对和首条消息发送。
- [ ] 第二个配对关系无法在未解除当前关系时建立。
- [ ] 安全号码在双方设备上显示一致。
- [ ] 被替换或移除的设备无法接收撤销后的新消息和新共享项密钥。
- [ ] 解绑前清楚展示对本机、对端和服务端数据的不同影响。

### 3.2 Chat：即时沟通入口

#### 3.2.1 MVP 消息类型

| 类型 | P0 行为 | 限制原则 |
|---|---|---|
| 文本 | 纯文本、emoji、链接识别 | 单条上限由客户端与协议共同限制 |
| 图片 | 压缩图/原图选项、全屏查看 | 明文只在授权设备本地解密 |
| 文件 | 发送附件、进度、失败重试 | MVP 单文件目标上限 100MB，可按基础设施调整 |
| 引用回复 | 显示被引用消息摘要并可跳转 | 原消息失效时显示“原内容不可用” |
| 系统事件 | 共享项创建、完成、Waiting、约定确认等 | 不允许伪装成用户消息 |

语音消息与位置分享进入 P1，不阻塞核心闭环验证。

#### 3.2.2 消息基础能力

- 发送状态：发送中、已送达、发送失败。
- 已读回执与输入状态均可按关系关闭，默认值需在隐私评审后确定。
- 支持对自己的消息发起撤回；撤回传播到对方已授权设备。
- 撤回不等于抹除对方已截图、导出或在受控范围外复制的内容。
- “提醒我”是仅本人可见的本地提醒，不自动创建共享项。

#### 3.2.3 常规与阅后即焚模式

| 模式 | 内容生命周期 | 可保存到 Space | 搜索 |
|---|---|---|---|
| 常规模式 | 持续保存，直到撤回、删除或关系解除 | 是 | 是 |
| 阅后即焚 | 按查看后/发送后倒计时销毁 | **MVP 禁止** | 否 |

规则：

- 模式切换对双方清晰可见，只影响切换后的新消息。
- 焚毁模式采用明显但克制的视觉状态，显示倒计时起点与时长。
- 焚毁消息不得收藏、转为待办/笔记/约定，也不得成为 Shared Item 的来源。
- 如果用户确实需要保留，应先切回常规模式并重新发送；避免单方保存破坏双方对焚毁语义的预期。
- Android 在平台允许时阻止敏感页面截屏；iOS 等无法绝对阻止的系统提供检测后提示、后台遮罩和可选水印。
- 产品不得宣称能阻止另一台相机拍摄屏幕。

#### 3.2.4 端到端加密

- 消息、Shared Item 负载、文件内容和 Activity 内容采用成熟、经审计的端到端加密方案。
- 身份私钥和内容密钥不以可解密形式上传服务端。
- 密钥保存在系统安全存储能力中；本地数据库中的敏感字段加密。
- 具体算法、密钥轮换、多设备会话和附件密钥封装由安全架构文档确定，不在 PRD 中自行组合密码学原语。
- 安全号码变化、设备新增和密钥重建必须对双方可见。

### 3.3 统一动作：保存到 Space

“保存到 Space”是 M2Y 最重要的跨层交互。

#### 3.3.1 入口

- 长按一条常规消息。
- 多选连续或非连续的常规消息。
- 图片、链接和文件的更多菜单。
- 分享面板中的“保存到 Space”（仅处理已在 M2Y 内的内容，外部分享导入为 P1）。

#### 3.3.2 动作面板

```text
保存到 Space

📌 收藏
☑ 变成待办
📝 保存为笔记
🤝 记录为约定
```

文件消息无需再次上传，发送成功后自动出现在 Space 的文件筛选中；用户仍可将文件关联到待办、笔记或约定。

#### 3.3.3 默认填充

| 目标类型 | 默认内容 |
|---|---|
| 收藏 | 消息摘要、链接/媒体、来源消息 |
| 待办 | 首条消息作为标题候选，其余作为说明，默认未指派 |
| 笔记 | 多条消息按原顺序生成可编辑草稿 |
| 约定 | 多条消息生成草稿，默认进入待编辑状态而非直接确认 |

系统可以使用端侧规则提供标题候选；MVP 不把明文发送到云端 AI。

#### 3.3.4 保存结果

- 创建后在 Chat 中插入轻量 Shared Item 卡片或系统事件。
- Shared Item 保存 `sourceMessageIds` 与一份经双方可见的来源快照。
- 点击“查看原始聊天”定位到最早来源消息，并高亮关联消息。
- 若原消息之后被撤回，来源入口显示不可用；Shared Item 的显式保存内容仍保留，除非用户同时删除该 Item。
- 创建者可以在最终确认前取消；已同步给对方后，删除遵循共享删除规则并产生 Activity。

#### 3.3.5 验收标准

- [ ] 单条消息在 3 次操作内保存为任一支持类型。
- [ ] 多选消息的顺序、发送者与时间语境正确保留。
- [ ] 创建后的 Item 可跳回准确聊天位置。
- [ ] 焚毁消息的菜单中不出现“保存到 Space”。
- [ ] 保存失败不会产生无来源的重复 Item。

### 3.4 Space Home

Space Home 不先问“你要打开哪个工具”，而是回答三个问题：

1. 什么需要我处理？
2. 我们接下来要做什么？
3. 我们最近留下或改变了什么？

#### 3.4.1 首页区域

| 区域 | 内容 | 排序 |
|---|---|---|
| 需要你 | 指派给我的未完成待办、正在等我的待办、待我确认的约定 | 超期优先，其次按截止/更新时间 |
| 接下来 | 所有带日期的活跃 Shared Item | 按时间升序，默认显示未来 7 天与已超期项 |
| 置顶 | 双方置顶的 Shared Item | 最近置顶优先，MVP 建议最多 6 项 |
| 最近更新 | 最近创建或发生有效变更的 Shared Item | 更新时间倒序，合并同一 Item 的连续变更 |

空状态必须给出具体动作，例如“长按一条消息，保存到 Space”。

#### 3.4.2 类型筛选

Space Home 下方提供：

```text
全部  收藏  待办  笔记  文件  约定
```

这些是同一 Shared Item 集合的筛选器，不是五套一级 Tab。

#### 3.4.3 “需要你”判定

任一条件成立即进入：

- `Task.assignee` 包含当前用户，且状态为 `open` 或 `doing`。
- `Task.status = waiting` 且 `waitingFor = 当前用户`。
- `Agreement.status = pending_confirmation` 且当前用户尚未确认当前版本。

完成、归档、仅等待对方的内容不出现在当前用户的“需要你”中。

### 3.5 Shared Item 通用能力

#### 3.5.1 通用字段

- 类型、标题/摘要、创建者、创建时间、更新时间。
- 来源消息引用与来源快照。
- 生命周期：活跃、归档、已删除。
- 日期/时间（可选）。
- 置顶状态（可选）。
- 与其他 Shared Item 的关联（P1 支持手动关联；P0 只保留系统产生的关系）。

#### 3.5.2 通用动作

- 打开详情。
- 置顶 / 取消置顶。
- 在聊天中讨论。
- 查看原始聊天。
- 归档 / 恢复。
- 删除。
- 复制链接仅限 M2Y 内部深链，不产生公开链接。

#### 3.5.3 在聊天中讨论

Shared Item 不建立评论区。点击“在聊天中讨论”后：

1. 跳转 Chat。
2. 输入框上方显示“正在讨论：{Item 标题}”。
3. 用户发送的下一条消息关联该 Item，并显示小型上下文标签。
4. 用户可主动关闭上下文；引用该讨论消息时继承关联。

Item 详情页展示“相关聊天”入口，但不复制完整消息流。

#### 3.5.4 置顶与收藏的区别

- **收藏（Pin Item）**是一种 Shared Item 类型：保存一个以后可能再用的消息、链接、图片或片段。
- **置顶（isPinned）**是任意 Shared Item 的排序属性：待办、笔记、文件、约定和收藏都可置顶。

中文 UI 使用“收藏”和“置顶”两个词，避免都叫 Pin。

### 3.6 收藏项（Pin）

#### 3.6.1 目标

为“这个以后可能有用，但现在不需要结构化”的信息提供最低成本入口。

典型内容：地址、Wi-Fi 密码、航班号、截图、证件副本、链接、一句说明。

#### 3.6.2 能力

- 从单条消息一键收藏。
- 自动显示内容预览、发送者、保存者和来源时间。
- 可补充简短标题。
- 可转为待办、笔记或约定；转换后默认保留原收藏，用户可选择归档收藏。
- 可置顶、搜索、归档和删除。
- 敏感内容由用户主动保存；产品不自动识别或上传分析。

### 3.7 待办（Task）

#### 3.7.1 双人责任模型

负责人只有四种表达：

- 未指派。
- 我。
- 对方。
- 双方。

MVP 不做团队成员、子任务、项目、标签体系和权限矩阵。

#### 3.7.2 状态

```text
待处理 Open
  ↓
进行中 Doing
  ↓
等待 Waiting ── 指明正在等谁
  ↓
已完成 Done
```

- 状态允许按实际情况前后切换。
- 进入 Waiting 时必须选择 `waitingFor` 为我、对方或双方，并可填写一句“在等什么”。
- 被等待的一方在 Space Home 看到“正在等你”。
- “完成”默认不要求对方二次确认；需要双方确认的结论应使用 Agreement。

#### 3.7.3 字段与能力

| 字段/能力 | MVP 规则 |
|---|---|
| 标题 | 必填，简短描述行动 |
| 说明 | 可选，支持纯文本与来源消息 |
| 负责人 | 未指派 / 我 / 对方 / 双方 |
| 状态 | Open / Doing / Waiting / Done |
| 日期 | 可选；一个截止日期时间 |
| 提醒 | 可选；在相关授权设备本地调度 |
| 讨论 | 回到 Chat，不建评论区 |
| 视图 | 统一列表与筛选，不做看板 |

#### 3.7.4 关键事件回流

以下变化在 Chat 产生合并后的系统事件：

- 创建并指派。
- 进入“正在等你”。
- 完成。
- 重新打开已完成任务。

普通标题编辑、日期微调仅进入 Activity，避免刷屏。

### 3.8 笔记（Note）

#### 3.8.1 定位

笔记用于把多条消息或共同信息整理为一份轻量、持续更新的文本，不做“小型 Notion”。

#### 3.8.2 MVP 能力

- 普通富文本编辑体验：标题、段落、列表、清单、加粗、链接。
- 可识别常用 Markdown 快捷输入，但不把“Markdown”作为用户概念或文件格式要求。
- 自动保存和双端同步。
- 支持插入聊天消息引用、图片和已有文件引用。
- 编辑时采用乐观锁/版本号；发生并发冲突时保留双方版本，由下一位编辑者选择合并，不能静默覆盖。
- 保存少量最近版本用于误操作恢复；MVP 目标为最近 10 个版本或 7 天，以先到条件为准。
- 支持在 Chat 中发送笔记卡片和发起讨论。

#### 3.8.3 MVP 不做

- 同时实时编辑与协同光标。
- CRDT 自动合并。
- 100 个版本、差异对比和任意版本树。
- 自动目录、数据库、模板市场。
- HTML/PDF 等完整导出体系；统一数据导出另行处理。

### 3.9 文件（File）

#### 3.9.1 定位

Space 中的“文件”不是独立网盘，而是**这段双人关系里所有常规聊天文件的索引视图**。

#### 3.9.2 自动索引

- 常规聊天中的文件发送成功后，自动建立一个 File Shared Item。
- 文件二进制只存一份加密资产；Chat 卡片与 Space 文件视图引用同一资产，不重复上传。
- File Item 展示文件名、类型、大小、发送者、发送时间和来源消息。
- 文件名及用户填写的描述作为加密内容处理；服务端只使用不可读的对象标识和必要传输字段。
- 图片是否默认进入文件筛选由设置控制；MVP 默认仅索引“文件附件”，图片在“媒体”入口聚合可放 P1。

#### 3.9.3 文件操作

- 打开、下载到本机、分享回当前 Chat。
- 置顶、归档、搜索文件名。
- 关联到待办、笔记或约定。
- “从 Space 隐藏”只归档索引，不删除 Chat 中的附件。
- “删除文件”删除底层加密资产，并使 Chat 与所有关联入口显示不可用；若存在关联项，删除前必须列出影响并二次确认。

#### 3.9.4 MVP 不做

- 手动文件夹树、网盘式独立上传首页。
- 自定义标签系统和批量文件管理。
- 2GB 大文件、分布式碎片营销能力和容量套餐。
- 服务端明文预览或全文索引。

### 3.10 约定（Agreement）

#### 3.10.1 定位

Agreement 表达的不是“我记录了一件事”，而是“**我们确认了同一件事**”。它适用于工作结论、时间安排、责任分工、预算共识和生活约定。

#### 3.10.2 字段

- 标题。
- 约定正文。
- 可选日期/生效时间。
- 来源消息或其他 Shared Item 引用。
- 当前内容版本号。
- 双方对当前版本的确认状态与确认时间。

#### 3.10.3 状态

```text
草稿 Draft
  ↓ 发起确认
等待确认 Pending confirmation
  ├─ 双方确认 → 已确认 Confirmed
  └─ 请求修改 → 修改中 Changes requested

已确认内容被修改
  ↓
生成新版本，旧确认失效，重新等待双方确认
```

规则：

- 创建者保存草稿不代表对方同意。
- 发起确认时冻结一个内容版本；每次确认都绑定 `agreementId + version`。
- 双方都确认同一版本后才显示“双方已确认”。
- 任一方请求修改时可填写简短原因，讨论回到 Chat。
- 已确认版本可查看历史快照；编辑会产生新版本，不覆盖旧版本。
- 删除或归档不等于否认过去的确认记录；UI 要明确区分。

#### 3.10.4 法律与安全边界

- MVP 中的确认是 M2Y 应用内的双方确认记录，不等同于法定电子签名、公证或证据保全。
- MVP 不承诺 RFC 3161 可信时间戳、第三方 TSA、不可篡改哈希链或具法律效力的 PDF。
- 可在后续版本经法务与安全评估后提供可验证导出；不得提前使用“可作证”作为营销承诺。

#### 3.10.5 验收标准

- [ ] 仅一方确认时不得显示“双方已确认”。
- [ ] 双方确认必须指向完全相同的内容版本。
- [ ] 修改已确认内容后，界面立即取消当前版本的已确认状态并保留旧版本。
- [ ] 对方可请求修改并一键回到 Chat 讨论。

### 3.11 Activity

#### 3.11.1 目标

Activity 提供轻量的协作感知，让双方知道对方是否改过、做过或确认过，而不建设复杂通知中心。

示例：

```text
今天
14:32  对方确认了「产品报价」
13:40  你完成了「修改首页」
11:22  对方更新了「日本行程」

昨天
21:03  你发送了 contract-v3.pdf
```

#### 3.11.2 规则

- Activity 由真实对象变更自动产生，用户不能手工创建或编辑。
- 事件负载端到端加密；服务端只同步密文事件。
- 连续编辑同一 Item 在短时间内合并为“更新了”，不逐字记录。
- 默认展示最近活动；更早内容通过分页加载。
- Activity 不等于审计日志，不承诺法律完整性。
- 打开 Activity 不触发强提醒，也不制造“已读压力”。

#### 3.11.3 进入 Activity 的事件

- Shared Item 创建、类型转换、归档、恢复和删除。
- 待办指派、Waiting、完成、重新打开。
- 笔记发生有效保存。
- 文件发送、归档和删除。
- 约定发起确认、确认、请求修改、双方确认、生成新版本。
- 置顶与取消置顶。

### 3.12 时间视图

- 时间是 Shared Item 的跨类型属性，不在 MVP 中建设独立 Calendar 产品。
- “接下来”按天分组展示带日期的待办和约定。
- 支持今天、未来 7 天、稍后和已超期分组。
- 点击项目进入原 Item；提醒由相关设备本地调度。
- P1 可增加轻量月视图、重复规则和时间提议；外部日历同步不属于 P0。

### 3.13 统一搜索

#### 3.13.1 搜索范围

- 常规聊天消息。
- 收藏、待办、笔记、文件名、约定。
- 结果可按“消息 / Space / 文件”切换，也可按 Shared Item 类型筛选。

#### 3.13.2 隐私规则

- 全文索引在授权设备本地、解密后建立。
- 服务端不接收查询词，不建立明文内容索引。
- 新设备同步密文后在本地重建索引。
- 焚毁消息不进入索引；已销毁内容必须从本地索引移除。

### 3.14 隐私与控制层

#### 3.14.1 应用访问

- 支持 Face ID / Touch ID / Android 生物识别与独立 PIN。
- 进入后台立即遮罩；可配置后台 N 分钟后清除内存中的已解密内容。
- 系统任务切换器不显示聊天或 Space 内容预览。
- 生物识别失败后的降级策略遵循平台安全能力，不自行存储生物信息。

#### 3.14.2 截屏、录屏与水印

- Android 在能力允许时对敏感页面启用安全窗口。
- iOS 在检测到录屏/投屏时立即遮罩敏感内容；截图检测通常发生在截图后，只能告警，不能绝对阻止。
- 可选水印包含双方截断 ID 与时间；默认策略需通过可用性测试。
- 截屏事件是否通知对方由模式和设置决定，产品须说明平台限制与误差。

#### 3.14.3 诱饵界面（P1）

- 输入备用 PIN 后进入与真实数据完全隔离的本地诱饵界面。
- 诱饵数据不引用真实对象、缩略图、搜索索引或通知。
- 紧急删除必须有防误触设计；上线前进行专门威胁建模。

#### 3.14.4 本地安全记录

记录本设备发生的：

- 成功/失败解锁。
- 设备授权与移除。
- 安全号码变化。
- 数据导出与删除。
- 本平台能检测到的截屏/录屏事件。

记录默认只保存在本机，并可随本机数据删除。

### 3.15 系统层

#### 3.15.1 密文同步与离线投递

- 服务端可临时或持久保存消息、Shared Item 和文件的密文，以支持离线投递与多设备同步。
- 服务端不持有内容解密密钥，不执行内容级搜索、推荐或广告分析。
- 运行所需元数据（例如投递队列、设备令牌、对象大小、时间、IP/风控日志）按最小化原则收集并设置保留期。
- 对外统一表述为“服务端零明文 / 产品方不可解密”，不使用“服务器完全不存数据”或“绝对零元数据”。

#### 3.15.2 通知与提醒

- 推送通知默认不包含消息或 Shared Item 明文；用户可在设备端选择是否展示本地解密后的预览。
- 待办/约定提醒优先在授权设备本地调度。
- “紧急”不得默认绕过系统勿扰；只能使用平台明确允许且经用户授权的通知等级。
- M2Y 的专注设置只能控制 M2Y 自身通知，不能承诺静默其他 App。

#### 3.15.3 数据导出

- 用户可在本机导出聊天与 Space 数据的加密包。
- 导出前要求应用解锁和二次确认。
- 明文导出必须明确提示风险，并在系统分享完成后清理临时文件。
- 导出行为写入本地安全记录。

#### 3.15.4 删除

- 删除请求应区分：本地删除、共享对象删除、底层文件资产删除、关系解除、账户删除。
- 服务端对密文执行可验证的删除队列与保留期策略。
- 已被对方导出、截图、备份或在离线受控范围外复制的内容无法由 M2Y 保证删除。

## 4. 核心对象与状态规则

### 4.1 Shared Item 类型

| 类型 | 核心问题 | 独有状态 |
|---|---|---|
| Pin / 收藏 | 什么以后还要用？ | 无额外状态 |
| Task / 待办 | 谁要做什么，现在到哪一步？ | Open / Doing / Waiting / Done |
| Note / 笔记 | 哪些信息需要被持续整理？ | 编辑版本 |
| File / 文件 | 我们在聊天中传过哪些文件？ | 可用 / 处理中 / 失败 / 不可用 |
| Agreement / 约定 | 我们共同确认了什么？ | Draft / Pending / Changes requested / Confirmed |

### 4.2 通用生命周期

```text
Active（活跃）
  ├─ Archive → Archived（归档）
  └─ Delete  → Deleted（已删除）

Archived 可恢复为 Active。
Deleted 进入短暂撤销窗口后，从授权设备和服务端密文存储中按策略清理。
```

### 4.3 来源关系

每个 Shared Item 可以记录：

- `sourceMessageIds`：一条或多条来源消息。
- `sourceSnapshot`：创建时明确保存的内容快照。
- `relatedItemIds`：系统产生的关联；手动关联进入 P1。
- `discussionMessageIds`：通过“在聊天中讨论”形成的消息关系。

来源快照是 Shared Item 内容的一部分。原消息被撤回不会自动改写已经共同保存的 Item，但来源跳转将显示不可用。

### 4.4 双人操作权限

MVP 中双方对 Space 内容拥有对等可见性，不建设复杂权限：

- 任一方可创建、编辑、置顶、归档和发起讨论。
- 待办状态可由双方改变；Activity 记录操作者。
- 约定确认只能由对应身份本人执行，不能代对方确认。
- 删除共享内容影响双方，必须二次确认并通知对方。
- 对需要“仅自己可见”的内容，使用本地“提醒我”，不放入 Space。

### 4.5 冲突规则

- 状态变更使用对象版本号与幂等操作 ID，避免重复应用。
- 待办等结构化字段发生冲突时，以服务端确认的操作顺序收敛，并在 Activity 中保留双方操作。
- 笔记正文发生并发编辑时，不做静默“最后写入覆盖”；保留冲突副本并提示合并。
- 约定确认绑定内容版本；任何正文变更生成新版本并使新版本重新等待确认。

## 5. 信息架构与页面结构

### 5.1 一级导航

```text
聊天（默认）  |  Space  |  设置
```

- 默认打开 Chat，体现“聊天是入口”。
- Space 图标可显示“需要你”的数量，不显示一般 Activity 数量以降低通知压力。
- 任意 Item 卡片都可在 Chat 与 Space 之间双向跳转。

### 5.2 页面层级

```text
M2Y App
│
├── 启动 / 解锁
│   └── 生物识别 / PIN / 后台遮罩
│
├── Chat
│   ├── 对方状态与安全提示
│   ├── 常规 / 焚毁模式切换
│   ├── 消息流与 Shared Item 卡片
│   ├── 长按 / 多选 → 保存到 Space
│   └── Item 讨论上下文输入框
│
├── Space Home
│   ├── 需要你
│   ├── 接下来
│   ├── 置顶
│   ├── 最近更新
│   ├── 类型筛选：全部 / 收藏 / 待办 / 笔记 / 文件 / 约定
│   ├── Activity
│   ├── 时间视图
│   └── 统一搜索
│
├── Shared Item 详情
│   ├── 类型专属内容与状态
│   ├── 来源聊天
│   ├── 相关聊天
│   ├── 置顶 / 归档 / 删除
│   └── 在聊天中讨论
│
└── 设置
    ├── 身份与恢复
    ├── 关系与安全号码
    ├── 设备管理
    ├── 隐私与通知
    ├── 存储与导出
    └── 解绑 / 删除账户
```

### 5.3 导航规则

- 任一核心动作在 3 次点击内到达。
- 从来源消息打开 Item 后，返回键回到原聊天位置。
- 从 Item 点击“查看原始聊天”时，保持返回到 Item 的路径。
- 筛选状态在本次会话中保留；重新进入 Space 默认回首页。
- 搜索结果明确标注来自 Chat 还是 Space，避免同一文件的两个视图被误认为重复内容。

## 6. 关键用户流程

### 6.1 首次使用与配对

```text
启动 App
  ↓
生成设备身份与 M2Y-ID
  ↓
设置本地显示名、应用锁与恢复方式
  ↓
选择配对方式：扫码 / M2Y-ID / 握手码
  ↓
双方确认安全号码
  ↓
进入 Chat
  ↓
首次引导：长按重要消息可“保存到 Space”
```

### 6.2 消息保存为待办

```text
长按消息
  ↓
保存到 Space → 待办
  ↓
自动填充标题与来源
  ↓
选择负责人；日期可选
  ↓
创建
  ↓
Chat 出现待办卡片；Space Home 按责任显示
  ↓
负责人更新为 Doing / Waiting / Done
  ↓
关键状态回到 Chat，完整历史进入 Activity
```

### 6.3 多条消息保存为约定

```text
多选相关消息
  ↓
保存到 Space → 约定
  ↓
生成可编辑草稿，保留消息顺序和来源
  ↓
编辑标题与正文
  ↓
发起确认（冻结版本 V1）
  ↓
双方分别确认 V1
  ↓
显示“双方已确认”与各自确认时间
```

若对方请求修改：

```text
请求修改 → 回到 Chat 讨论 → 修改生成 V2 → 双方重新确认 V2
```

### 6.4 从 Space 回到 Chat 讨论

```text
打开 Shared Item
  ↓
点击“在聊天中讨论”
  ↓
Chat 输入框显示 Item 上下文
  ↓
发送消息
  ↓
消息显示 Item 标签，Item 可跳转到相关聊天
```

### 6.5 文件自动索引

```text
在常规 Chat 发送文件
  ↓
客户端加密并上传，服务端保存密文资产
  ↓
发送成功
  ↓
同一文件自动出现在 Space → 文件筛选
  ↓
用户可置顶、归档或关联到其他 Shared Item
```

### 6.6 Waiting 闭环

```text
我完成自己的步骤
  ↓
将待办设为 Waiting，选择“正在等对方”
  ↓
对方的 Space Home 出现“正在等你”
  ↓
对方处理后选择 Doing / Done，或切换为“正在等我”
  ↓
关键变化回到 Chat
```

### 6.7 焚毁消息流程

```text
双方进入焚毁模式
  ↓
发送敏感消息
  ↓
接收方查看，开始倒计时
  ↓
菜单不提供保存、复制、转发
  ↓
倒计时结束，授权设备删除内容与本地索引
  ↓
切回常规模式后不显示消息正文
```

| 待办 | 负责人、Open/Doing/Waiting/Done、日期、本地提醒 |

### 7.2 P1：在核心闭环成立后完善

- 多设备同时在线与完整授权、桌面端。
- 语音消息、位置分享、外部内容导入。
- 笔记更清晰的版本恢复与手动合并工具。

- 轻量月视图、重复日期、时间提议。
- 手动关联多个 Shared Item。
- 加密导出、可验证的约定历史导出。
- 诱饵界面与更细的本地安全记录。
- Activity 筛选与更长历史。

### 7.3 P2：仅在真实需求证据充分后评估

- CRDT 实时协同、协同光标。
- 看板、子任务、复杂标签和项目分组。
- 完整 Calendar 与外部双向日历同步。
- 大文件、独立文件空间和容量订阅。
- 第三方可信时间戳、数字签名、法律存证方案。
- Tor/混淆网络、高级元数据防护。
- 端侧 AI 摘要与结构化建议。
- 开放 API 与外部集成。

### 7.4 明确从 MVP 移除的原需求

| 原需求 | MVP 处理 |
|---|---|
| Markdown 笔记产品心智 | 改为普通富文本；仅支持部分快捷输入 |
| CRDT + 协同光标 | 移至 P2，P0 用冲突副本避免丢失 |
| 100 个版本、TOC、HTML/PDF 导出 | 移除；仅保留有限误操作恢复 |
| 待办看板、四级优先级、复杂标签 | 移除；突出负责人、Waiting 和日期 |
| 独立文件仓、2GB、分布式碎片、容量套餐 | 改为聊天文件自动索引 |
| 完整月/周日历和重复规则 | 改为 Shared Item 时间视图 |
| RFC 3161、电子签名、不可篡改 PDF | 改为应用内双方版本确认 |
| Tor、硬件密钥、高级审计 | 延后至威胁模型与需求验证之后 |

## 8. 非功能需求

### 8.1 安全与隐私

| 要求 | MVP 标准 |
|---|---|
| 内容机密性 | 消息、Shared Item、文件与 Activity 端到端加密 |
| 服务端能力边界 | 不持有内容解密密钥，不读取内容，不建立明文全文索引 |
| 本地存储 | 敏感数据库字段加密，密钥使用系统安全存储 |
| 前向安全 | 采用成熟协议能力；具体保证以安全设计和审计结果为准 |
| 传输安全 | E2EE 之外仍使用现代传输层加密与证书校验 |
| 通知隐私 | 默认推送无明文；本地预览由用户控制 |
| 日志 | 客户端与服务端日志禁止写入消息、标题、文件名和搜索词明文 |
| 第三方 SDK | MVP 禁止广告 SDK 与跨应用追踪 SDK；分析能力最小化 |
| 安全验证 | 上线前完成威胁建模、依赖审计、渗透测试与删除验证 |

### 8.2 数据最小化与保留

- 服务端仅保存提供投递、同步、反滥用和可靠性所必需的数据。
- 对未投递密文、运行日志、IP/风控信息、推送令牌分别设定明确保留期。
- 密文内容与元数据使用不同访问控制和审计策略。
- 用户可在设置中查看设备、存储用量与删除入口。
- 数据政策必须准确描述服务端保存的密文与必要元数据，禁止使用“完全无痕”误导。

### 8.3 性能目标

| 指标 | MVP 目标 |
|---|---|
| 文本消息发送至送达 | 正常网络 P95 < 1 秒 |
| Space Home 首屏 | 已有本地数据时 P95 < 500ms |
| Shared Item 本地创建反馈 | < 200ms；同步状态异步展示 |
| 本地搜索首批结果 | 1 万条消息与 1 千个 Item 下 P95 < 1 秒 |
| 100KB 笔记打开 | P95 < 500ms |
| 崩溃率 | Crash-free sessions ≥ 99.5% |
| 同步正确性 | 已确认操作最终收敛，无静默内容丢失 |

具体网络时延不以“直连必达”作承诺，应在目标市场和真实设备上压测后校准。

### 8.4 离线与同步

- 离线可浏览本机已有内容、创建/编辑 Shared Item 和发送待处理消息。
- 重连后自动同步，界面显示“等待同步 / 已同步 / 失败”。
- 所有变更具幂等操作 ID，重复投递不产生重复 Item 或重复确认。
- 笔记冲突不得静默丢失任一方文本。
- 约定确认在离线冲突时必须重新校验内容版本。

### 8.5 可用性与无障碍

- 核心路径支持屏幕阅读器、动态字体和足够色彩对比。
- 状态不能只靠颜色表达，必须配合文字/图标。
- “删除”“解绑”“删除文件资产”等不可逆操作必须说明影响范围。
- 加密操作对普通用户透明，但安全号码变化与设备加入不能被隐藏。
- 首次配对到首条消息不超过 3 个主要步骤；保存到 Space 不超过 3 次操作。

### 8.6 平台范围

| 平台 | 版本 | 优先级 |
|---|---|---|
| iOS | 最低版本由研发根据安全 API 与市场覆盖确定 | P0 |
| Android | 最低版本由研发根据安全 API 与市场覆盖确定 | P0 |
| macOS / Windows | 与多设备能力一并规划 | P1 |
| Web | 需单独评估浏览器密钥与本地安全风险 | P2 |

## 9. 指标体系

### 9.1 北极星指标

> **每周双向协作 Pair 数（Weekly Mutual Space Pairs，WMSP）**

定义：在任意滚动 7 天内，双方都对**同一个 Shared Item**完成至少一次有效协作动作的活跃 Pair 数。

有效协作动作包括：

- 从 Chat 保存/创建 Shared Item。
- 编辑笔记并成功同步一个新版本。
- 接受指派、改变待办状态、设置或响应 Waiting。
- 发起、确认或请求修改约定。
- 围绕 Item 发起关联讨论并由另一方继续响应。

不计入：

- 仅打开 App、仅浏览 Space、仅收到推送。
- 同一方反复编辑或创建多个 Item。
- Activity 自动生成、系统同步和后台索引。
- 双方只聊天但没有任何 Space 协作。

选择该指标的原因：它同时验证“聊天成功沉淀”“共享项对双方有用”和“双人关系真实协作”，不会把团队带向单纯增加消息数量。

### 9.2 北极星率指标

> **每周双向 Space 协作率 = WMSP / 每周活跃 Pair 数**

“每周活跃 Pair”定义为 7 天内双方均至少打开一次 M2Y 或成功收发一次消息的 Pair。绝对数用于观察增长，比例用于观察产品价值是否被稀释。

### 9.3 漏斗指标

| 阶段 | 指标 | 定义 |
|---|---|---|
| 建立关系 | 配对成功率 | 发起配对后 24 小时内完成双方确认的比例 |
| 首次价值 | 首次 Save to Space 转化 | 配对后 7 天内至少保存 1 个 Item 的 Pair 比例 |
| 双向激活 | 7 日双向协作率 | 配对后 7 天内双方在同一 Item 上发生有效动作的 Pair 比例 |
| 持续使用 | W4 Mutual Space Retention | 第 4 周再次成为 WMSP 的首周激活 Pair 比例 |
| 行动闭环 | 待办闭环率 | 创建后 14 天内进入 Done 的待办比例；按有无日期分层 |
| 相互响应 | Waiting 响应中位时长 | 进入“正在等你”到对方有效动作的时间 |
| 共识形成 | 约定确认率 | 发起确认后 7 天内双方确认同一版本的比例 |
| 信息找回 | 搜索成功代理指标 | 搜索后 60 秒内打开结果或跳转来源的查询比例 |

指标目标值在封闭 Beta 收集 4 周基线后设定，不在缺少真实数据时写入任意百分比。

### 9.4 体验与安全护栏指标

- Shared Item 误删/撤销率。
- 重复 Item 率和同步冲突率。
- 笔记冲突导致的内容丢失事件：目标为 0。
- 推送关闭率、通知投诉率和“需要你”长期积压率。
- 焚毁内容在本地缓存/索引残留的验证失败：目标为 0。
- 密钥泄露、越权读取、服务端获得明文的安全事件：一票否决。
- Crash-free sessions、消息失败率、文件上传失败率。

### 9.5 隐私友好的度量方式

- 不采集消息正文、Item 标题、笔记内容、文件名、搜索词或来源快照。
- 不使用第三方广告 ID 或跨应用身份。
- 使用轮换的随机 Pair 分析标识统计聚合事件，并设置短保留期。
- 分析事件只包含动作类别、对象类型、粗粒度时延和成功/失败，不包含内容。
- 设置中提供透明说明与适用地区要求的退出选择。

## 10. 迭代规划

迭代按“能否验证核心假设”排序，而不是按工具模块并行堆功能。周期为参考范围，需在团队规模、技术选型和安全评审后重新估算。

### 10.1 M0：安全与交互可行性（建议 3–4 周）

交付：

- 关系、设备、消息、Shared Item 的威胁模型。
- 端到端加密与多设备策略技术方案。
- Chat ↔ Space 点击原型与 8–12 位目标用户测试。
- 消息保存、Waiting、约定确认三条关键流程的可用性结论。
- 服务端数据清单与“零明文/不可解密”口径评审。

退出条件：

- 安全方案无已知致命缺口。
- 至少 80% 测试用户能在无讲解情况下把消息保存为正确类型并返回讨论。
- 用户能理解“收藏”和“置顶”、“待办完成”和“约定确认”的区别。

### 10.2 M1：Pair + Chat 内部 Alpha（建议 5–7 周）

交付：

- M2Y-ID、配对、安全号码、单台活跃设备与受控换机。
- 文本、图片、文件、引用、撤回与基本 E2EE。
- 常规/焚毁模式基本链路。
- 本地加密存储、后台遮罩、无明文通知。
- 密文投递、离线队列和基础同步监控。

退出条件：

- 内部测试中无跨 Pair 越权或明文服务端日志。
- 核心消息可靠性达到发布门槛。
- 焚毁内容通过本地数据库、缓存和搜索索引残留测试。

### 10.3 M2：Space 核心闭环封闭 Beta（建议 6–8 周）

交付：

- 统一 Save to Space。
- Space Home 与类型筛选。
- 收藏、待办（含 Waiting）、轻量笔记、文件自动索引、约定双方确认。
- 来源跳转、在 Chat 讨论、关键状态回流。
- Activity、本地统一搜索和本地提醒。
- 隐私友好型指标事件。

退出条件：

- 关键流程端到端验收全部通过。
- Beta 中出现稳定的 WMSP，而非仅单方创建。
- 无静默同步丢失、重复确认或约定版本错认。
- “需要你”被多数测试 Pair 认为有帮助而非制造压力。

### 10.4 M3：MVP 公测与质量收敛（建议 4–6 周）

交付：

- 性能、无障碍、错误恢复与空状态打磨。
- 设备管理、解绑、删除和加密导出基础能力。
- 第三方安全评估与修复。
- 数据保留政策、隐私说明、平台合规材料。
- Beta 指标基线和 P1 决策报告。

退出条件：

- 通过第 12 节发布验收。
- 安全高危问题清零，中危问题有明确处置。
- W4 Mutual Space Retention 和用户访谈共同证明 Space 具有持续价值。

### 10.5 P1 决策原则

以下能力不是按时间自动进入开发，而是满足证据门槛后进入：

| 候选能力 | 进入条件示例 |
|---|---|
| 笔记实时协同 | 大量会话出现并发编辑，冲突副本明显损害体验 |
| 轻量月视图 | 带日期 Item 高频，且“接下来”无法满足回看/规划需求 |
| 文件标签/批量管理 | 每个活跃 Pair 的文件量与找回失败率持续上升 |
| 可验证约定导出 | 专业服务用户有明确付费意愿，且法务/安全方案成立 |
| 桌面端 | 移动端活跃 Pair 在工作场景中频繁中断或主动请求 |
| Tor/高级元数据防护 | 目标威胁模型、性能成本和运维能力均得到验证 |

## 11. 风险、限制与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| “两个人”市场过窄，聊天迁移成本高 | 高 | 用 Save to Space 与双向协作验证独特价值；不以聊天功能数量竞争 |
| Space 被做成五个低配工具 | 高 | 坚持 Space Home + Shared Item；类型仅作筛选，跨类型共用来源、讨论和 Activity |
| 单方创建、对方不响应 | 高 | NSM 强制双方在同一 Item 上有效行动；优化“需要你”与低摩擦响应 |
| E2EE + 多设备 +离线同步复杂 | 高 | M0 完成威胁模型；采用成熟协议与库；先单设备闭环，再扩多设备 |
| 笔记并发冲突 | 中 | MVP 不做实时协同；版本号检测，冲突时保留双方版本 |
| Agreement 被误认为法律合同 | 高 | 文案使用“应用内双方确认”；不宣称电子签名或证据效力 |
| “服务端零留存”误导 | 高 | 全面改为“服务端零明文/不可解密”；公开必要密文与元数据清单 |
| 截屏与远程删除被过度承诺 | 高 | 按平台写明能力限制；使用“尽力而为”，不使用“绝对防止/彻底远程擦除” |
| 匿名注册被滥用 | 高 | 配对必须双方确认；速率限制、设备风控、封禁与举报流程；不破坏 E2EE 内容隐私 |
| 本地设备失窃或 Root/越狱 | 高 | 应用锁、系统安全存储、后台遮罩、设备风险提示；明确端点安全边界 |
| 文件成本与滥用 | 中 | MVP 限制大小与类型风险扫描策略；密文配额、速率限制、可验证删除 |
| Activity/通知造成关系压力 | 中 | 只记录有效变更；合并事件；不展示过度在线状态；允许关闭非关键通知 |
| 本地搜索泄露 | 中 | 索引加密、锁屏不可用、焚毁/删除时清除索引、后台立即遮罩 |
| 指标采集破坏隐私信任 | 高 | 无内容事件、轮换随机标识、短保留期、透明说明、禁止广告追踪 SDK |

### 11.1 已知产品限制

- M2Y 无法控制接收者使用外部相机、系统备份或手工转录内容。
- 远程删除不能保证擦除已离线复制、导出或存在于受损设备中的内容。
- 不使用手机号/邮箱不等于网络级完全匿名；IP、推送服务和支付可能形成元数据。
- E2EE 会降低服务端找回、内容审核、云端搜索与智能推荐能力，这是产品有意接受的取舍。
- 丢失全部授权设备和恢复材料时，平台可能无法恢复历史内容。

## 12. MVP 发布验收

### 12.1 核心体验

- [ ] 用户可从注册到配对、聊天和首次 Save to Space 完成全链路。
- [ ] Space Home 能正确回答“需要你、接下来、置顶、最近更新”。
- [ ] 类型筛选不会产生五套割裂的一级导航。
- [ ] 收藏、待办、笔记、文件、约定均可从 Chat 到 Space，再回到 Chat。
- [ ] 任一 Shared Item 可查看来源或明确显示来源已不可用。
- [ ] Shared Item 不存在独立评论系统，“在聊天中讨论”工作正常。

### 12.2 状态正确性

- [ ] Waiting 必须指明正在等谁，并只进入对应用户的“需要你”。
- [ ] 约定只有双方确认同一版本后才显示“双方已确认”。
- [ ] 修改已确认约定会生成新版本并要求重新确认。
- [ ] Activity 操作者、对象、时间和动作准确，连续编辑能合并。
- [ ] 同一文件在 Chat 与 Space 中引用同一加密资产，不重复上传。
- [ ] 删除文件前正确显示所有受影响入口。

### 12.3 同步与离线

- [ ] 离线创建/编辑后重连能最终同步且不重复。
- [ ] 多端重复投递不会重复创建 Item、Activity 或确认记录。
- [ ] 笔记并发编辑不发生静默内容丢失。
- [ ] 约定离线确认不会确认错误内容版本。
- [ ] 删除、归档、恢复在双方设备最终收敛。

### 12.4 安全与隐私

- [ ] 服务端数据库、对象存储、队列与日志均不存在消息、标题、文件名、搜索词等内容明文。
- [ ] 服务端不持有可解密内容的密钥材料。
- [ ] 焚毁消息不能保存到 Space，销毁后不残留在本地数据库、缓存、缩略图和搜索索引。
- [ ] 锁屏、后台和任务切换器不泄露内容。
- [ ] 推送默认不含内容明文。
- [ ] 新设备、密钥变化和安全号码变化对双方可见。
- [ ] 删除、解绑、导出的范围和限制均有准确提示。
- [ ] 上线前安全高危问题为 0。

### 12.5 指标与运营

- [ ] 能在不采集内容的前提下计算 WMSP 与关键漏斗。
- [ ] 分析标识与 M2Y-ID、广告 ID 隔离并按策略轮换。
- [ ] 指标事件不包含标题、正文、文件名、搜索词或消息 ID 原值。
- [ ] 客服与故障排查流程不要求用户提交明文内容。

## 附录 B：逻辑数据模型

> 以下是产品逻辑模型，不是最终数据库结构。除路由与可靠性所需字段外，业务负载应作为端到端加密内容封装。

```typescript
type UserId = string;
type PairId = string;
type DeviceId = string;
type MessageId = string;
type SharedItemId = string;
type OperationId = string;

interface Identity {
  userId: UserId;
  m2yId: string;
  identityPublicKey: string;
  devices: DeviceSummary[];
  createdAt: number;
}

interface DeviceSummary {
  deviceId: DeviceId;
  publicKey: string;
  fingerprint: string;
  authorizedAt: number;
  revokedAt?: number;
}

interface Pairing {
  pairId: PairId;
  memberIds: [UserId, UserId];
  status: 'pending' | 'active' | 'ended';
  pairedAt?: number;
  endedAt?: number;
}

interface EncryptedEnvelope {
  envelopeId: string;
  pairId: PairId;             // 可使用不可枚举的路由标识
  senderDeviceId: DeviceId;
  ciphertext: string;
  keyEnvelopes: DeviceKeyEnvelope[];
  contentTypeHint: 'message' | 'shared_item' | 'activity' | 'operation';
  createdAt: number;
  expiresAt?: number;
}

interface DeviceKeyEnvelope {
  recipientDeviceId: DeviceId;
  wrappedContentKey: string;
}

interface MessagePayload {
  messageId: MessageId;
  senderId: UserId;
  type: 'text' | 'image' | 'file' | 'system';
  body: unknown;
  replyToMessageId?: MessageId;
  relatedItemId?: SharedItemId;
  mode: 'normal' | 'burn';
  burnRule?: {
    trigger: 'after_read' | 'after_send';
    delaySeconds: number;
  };
  createdAt: number;
}

type SharedItemType = 'pin' | 'task' | 'note' | 'file' | 'agreement';
type SharedItemLifecycle = 'active' | 'archived' | 'deleted';

interface SharedItemPayload {
  itemId: SharedItemId;
  pairId: PairId;
  type: SharedItemType;
  title?: string;
  body: PinBody | TaskBody | NoteBody | FileBody | AgreementBody;
  sourceMessageIds: MessageId[];
  sourceSnapshot?: SourceSnapshot[];
  discussionMessageIds: MessageId[];
  relatedItemIds: SharedItemId[];
  lifecycle: SharedItemLifecycle;
  isPinned: boolean;
  dateTime?: number;
  createdBy: UserId;
  createdAt: number;
  updatedBy: UserId;
  updatedAt: number;
  version: number;
}

interface SourceSnapshot {
  senderId: UserId;
  sentAt: number;
  content: unknown;
}

interface PinBody {
  preview: unknown;
  convertedToItemId?: SharedItemId;
}

interface TaskBody {
  description?: string;
  assignee: 'unassigned' | UserId | 'both';
  status: 'open' | 'doing' | 'waiting' | 'done';
  waitingFor?: UserId | 'both';
  waitingReason?: string;
  dueAt?: number;
  reminderAt?: number;
  completedAt?: number;
}

interface NoteBody {
  document: unknown;          // 编辑器结构化文档
  baseVersion: number;
  conflictCopyIds?: string[];
}

interface FileBody {
  assetId: string;
  fileName: string;
  mimeType: string;
  sizeBytes: number;
  senderId: UserId;
  sourceMessageId: MessageId;
  availability: 'processing' | 'available' | 'failed' | 'deleted';
}

interface AgreementBody {
  content: unknown;
  agreementVersion: number;
  status: 'draft' | 'pending_confirmation' | 'changes_requested' | 'confirmed';
  requestedBy?: UserId;
  confirmations: AgreementConfirmation[];
  previousVersionItemId?: SharedItemId;
}

interface AgreementConfirmation {
  userId: UserId;
  agreementVersion: number;
  confirmedAt: number;
  operationId: OperationId;
}

interface ActivityPayload {
  activityId: string;
  pairId: PairId;
  actorId: UserId;
  itemId: SharedItemId;
  action:
    | 'created'
    | 'updated'
    | 'assigned'
    | 'waiting'
    | 'completed'
    | 'reopened'
    | 'confirmation_requested'
    | 'confirmed'
    | 'changes_requested'
    | 'agreement_confirmed'
    | 'pinned'
    | 'unpinned'
    | 'archived'
    | 'restored'
    | 'deleted';
  createdAt: number;
  operationId: OperationId;
}
```

### B.1 数据模型约束

- `AgreementConfirmation` 只有在 `agreementVersion` 等于当前待确认版本时有效。
- `Task.status = waiting` 时 `waitingFor` 必填；其他状态应清空 `waitingFor`。
- `FileBody.assetId` 被 Chat Message 与 File Item 共同引用，不得重复存储同一资产。
- `sourceSnapshot` 不可引用焚毁消息。
- 所有写操作必须携带 `operationId` 与期望对象版本，用于幂等和冲突检测。
- 服务端不应解析 `SharedItemPayload`；上述字段在端到端加密负载中由客户端处理。

## 附录 C：服务端接口草案

> 接口仅表达产品能力。最终协议应优先采用端到端加密信封与操作日志，而不是让服务端理解 Todo、Note、Agreement 等业务明文。

```text
POST   /v1/identity/register              注册公开身份材料与设备公钥
POST   /v1/pair/request                   发起配对
POST   /v1/pair/confirm                   确认配对
POST   /v1/pair/end                       结束关系

POST   /v1/device/authorize/request       请求新设备授权
POST   /v1/device/authorize/confirm       已授权设备确认
POST   /v1/device/revoke                  撤销设备
GET    /v1/device/list                    获取本人设备清单

POST   /v1/envelope                       上传消息/Item/Activity 密文信封
GET    /v1/envelope/sync                  按游标拉取密文信封
POST   /v1/envelope/ack                   确认投递
DELETE /v1/envelope/:id                   删除符合策略的密文信封

POST   /v1/asset/init                     初始化加密资产上传
PUT    /v1/asset/:id/part                 上传密文分片
POST   /v1/asset/:id/complete             完成上传
GET    /v1/asset/:id                      下载密文资产
DELETE /v1/asset/:id                      删除密文资产

POST   /v1/push/token                     注册设备推送令牌
DELETE /v1/push/token/:id                 删除推送令牌

POST   /v1/account/delete/request         发起账户删除
GET    /v1/account/delete/status          查询删除状态
```

### C.1 接口原则

- 服务端接口不提供 `/todo`、`/note`、`/agreement/sign` 等可读取业务内容的明文端点。
- 服务端对密文信封执行认证、授权、幂等、顺序、配额和生命周期管理。
- 推送只携带不透明事件标识；客户端解锁后拉取并解密内容。
- 文件分片仅用于可靠上传，不将“分布式碎片”作为安全替代；真正的内容机密性来自正确的端到端加密和密钥管理。

## 附录 D：事件与通知规则

| 事件 | Activity | Chat 系统事件 | 推送 |
|---|---:|---:|---:|
| 收藏创建 | 是 | 轻量卡片 | 默认否 |
| 待办创建并指派给对方 | 是 | 是 | 是 |
| 待办普通编辑 | 合并记录 | 否 | 否 |
| 待办进入“正在等你” | 是 | 是 | 是 |
| 待办完成 | 是 | 是 | 可配置 |
| 笔记保存新版本 | 合并记录 | 否 | 默认否 |
| 文件发送成功 | 是 | 已有文件消息 | 已由消息控制 |
| 文件删除 | 是 | 是 | 是 |
| 约定发起确认 | 是 | 是 | 是 |
| 一方确认约定 | 是 | 是 | 是（通知另一方） |
| 双方确认约定 | 是 | 是 | 是 |
| 请求修改约定 | 是 | 是 | 是 |
| Item 置顶/取消置顶 | 是 | 否 | 否 |
| Item 归档/恢复 | 是 | 否 | 否 |
| Item 删除 | 是 | 是 | 是 |

通知内容默认只显示“M2Y 有一项更新”，不包含 Item 标题或正文。用户开启本地内容预览后，由设备解密并按操作系统能力展示。
