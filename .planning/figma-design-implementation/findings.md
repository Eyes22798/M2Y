Source: https://docs.expo.dev/versions/v56.0.0/sdk/sqlite/
- Expo SecureStore on Android encrypts SharedPreferences with Android Keystore, loses data on uninstall, excludes its entries from Auto Backup, and can return `null` after biometric enrollment invalidates an authenticated key. Therefore “missing key”, “invalidated key”, and “database cannot decrypt” need explicit recovery states. Source: https://docs.expo.dev/versions/v55.0.0/sdk/securestore/

Source: https://docs.expo.dev/versions/latest/sdk/local-authentication/
- Android Keystore can keep key material non-exportable and optionally hardware-backed, but SecureStore abstraction does not prove StrongBox residency. P1 must claim protected local key storage, not hardware-backed security, unless a native adapter later attests it. Source: https://developer.android.com/privacy-and-security/keystore
- Expo's app config defaults Android application backup to enabled; for an encrypted private collaboration database, `android.allowBackup: false` is the safest P1 default unless a tested key/data recovery design is added. Source: https://docs.expo.dev/versions/latest/config/app/
- The product PRD ultimately requires an independent PIN and recovery material, but implementing those safely also requires a native KDF/recovery-key lifecycle. The minimal foundation can instead expose destructive local reset after key loss and defer PIN/recovery without claiming recoverability.
- The user approved destructive local reset after SecureStore key loss/invalidation. Recovery UI must require a second confirmation and must remain fail-closed if database/key deletion is only partially successful.
- `PreviewWorkspaceProvider` is the single consumer boundary for Chat, Space, and detail commands, but its commands are currently synchronous reducer calls. Persistent repositories will require an explicit async command result and boot/hydration state instead of dispatch-then-return semantics.
- `AppProviders` currently mounts the workspace provider unconditionally. The secure boot boundary must gate private descendants until key access, SQLCipher open, migration, and hydration complete while keeping gesture/keyboard/safe-area providers outside that gate.
## 2026-08-20 — Security foundation decisions and SDK constraints

- Product decision approved: if the encrypted database exists but its key is missing or invalidated, Phase 1 offers only an explanation and a second-confirm destructive local reset; there is no recovery code, app PIN, or KDF fallback.
- The secure boot decision must combine two independent facts: the SecureStore envelope/key state and the physical SQLite database-file state. Silent key regeneration is forbidden whenever either side indicates prior initialization.
- Add direct SDK 56 dependencies for `expo-crypto` (asynchronous native random bytes) and `expo-file-system` (database-file existence). The SQLCipher key is 32 random bytes represented as validated hex.
- Use exclusive SQLite transactions for ordered migrations, parameterized/prepared statements for data, and explicit statement finalization.
- Authentication-bound key retrieval requires physical-device acceptance; emulator-only success cannot support the security claim.
- SQLCipher's official raw-key contract accepts exactly 64 hex characters as 32 key bytes. Key verification requires a real schema read after `PRAGMA key`; setting the pragma alone does not prove that an existing database opened successfully.
- SQLCipher key material and raw native error details must be kept out of logs/crash/analytics surfaces; application-facing failures use stable typed codes.
- Expo SDK 56's new File API expects a `file://` URI even though `defaultDatabaseDirectory` is exposed as an absolute path; normalize it before constructing `File` for database existence checks.
- Expo SQLite's `withExclusiveTransactionAsync` creates a separate connection. Because SQLCipher keys are connection-local, migrations, seed, and workspace writes must use `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` on the same connection that received `PRAGMA key`.
- Native Android evidence now proves SQLCipher wrong-key rejection, correct-key reopen, idempotent migration, recovery after SecureStore loss, persistent workspace reload, and destructive reset. Strong-biometric key binding still requires a physical device.

## 2026-08-20 — Next milestone planning

- The Android security/data-foundation task is archived and the worktree was clean before creating the next planning task.
- Cross-session memory preserves the agreed order: secure local foundation first, pairing/E2EE and sync second, richer product states later.
- `CLAUDE.md`, `README.md`, and the technology baseline prohibit JavaScript-authored cryptography and require an M0 native E2EE integration Spike before claiming real identity, pairing, safety numbers, or E2EE.
- The smallest honest next slice is therefore an Android-first native E2EE integration Spike, not a production pairing flow or decorative identity UI.
- Active planning task: `.trellis/tasks/08-20-android-e2ee-native-spike/`.
- The authoritative roadmap names Spike D as a 2–3 week native E2EE integration study covering identity, sessions, messages, attachment keys, device replacement/revocation, performance, package size, upgrades, licensing, maintenance, and external security review. M0 only requires a defensible feasibility conclusion before productization.
- The current `modules/m2y-crypto/` and `src/native/crypto/` contain boundary documentation only; no native E2EE implementation is installed.
- Signal's official `libsignal` repository publishes `org.signal:libsignal-client` plus `org.signal:libsignal-android`; the Android artifact includes `armeabi-v7a`, `arm64-v8a`, `x86`, and `x86_64`, so the current physical-device/emulator ABI matrix is technically covered.
- Signal states those packages are published for its own use. The project is AGPLv3 and third-party maintenance/support is not promised, so M2Y's source-distribution and app-store licensing strategy is a planning blocker before choosing it. Source: https://github.com/signalapp/libsignal
- Expo officially recommends a local Expo Module for app-specific Kotlin/Swift native code; local modules are autolinked and support the New Architecture. This matches the existing `modules/m2y-crypto/` boundary better than putting JNI/Kotlin changes into generated `android/`. Source: https://docs.expo.dev/modules/get-started/
- Product decision: M2Y accepts the AGPLv3 source-distribution obligations required to continue evaluating official `libsignal`. App-store-specific terms and corresponding-source delivery remain release gates, not assumptions.
- As of 2026-08-20, Signal's latest official release is `libsignal` v0.101.0 (2026-08-14). Releases are frequent, so the Spike must pin an exact version and record an explicit upgrade/rollback check instead of using a floating Maven version. Source: https://github.com/signalapp/libsignal/releases/tag/v0.101.0
- Current official Java tests use protocol v4 PQXDH with `PreKeyBundle`, `SessionBuilder`, `SessionCipher`, and `SignalProtocolStore`. They demonstrate first-message session establishment, bidirectional messages, out-of-order handling, duplicate rejection, corrupted-ciphertext failure, and untrusted-identity failure. Source: https://github.com/signalapp/libsignal/blob/main/java/client/src/test/java/org/signal/libsignal/protocol/SessionBuilderTest.java
- Because both the project baseline and current upstream API support this path, the minimum Spike cannot stop at loading JNI. It must exercise a real PQXDH/pre-key session plus subsequent ratcheted messages and durable state reload.
- The repository already uses Hermes + React Native New Architecture and generates all four Android ABIs. A local Expo Module can own Kotlin/libsignal code while app builds continue to narrow ABI via the existing `reactNativeArchitectures` Gradle property.
- `android/` is CNG-generated and currently adds only Google, Maven Central, and JitPack repositories. Signal's official Maven repository must be injected through persistent module/config-plugin configuration, never as a manual generated-project edit.
- Signal's official Maven metadata confirms both `org.signal:libsignal-client` and `org.signal:libsignal-android` currently publish exact version `0.101.0`; this is the version the plan will pin initially.
- The upstream artifacts are large before ABI/resource stripping: `libsignal-client-0.101.0.jar` is about 148 MB and `libsignal-android-0.101.0.aar` about 195 MB. The Spike must measure per-ABI APK/AAB delta and verify desktop native binaries/testing JNI are excluded, rather than estimating final package cost from source metadata.
- The POMs add Kotlin 2.2.20, kotlinx-coroutines 1.10.2, and kotlinx-serialization-json 1.9.0. Compatibility with Expo SDK 56's generated Kotlin/Gradle toolchain is therefore an explicit build gate.
- Sparse inspection of the pinned v0.101.0 tag resolved to signed release commit `b056faa6dd02961cff24064c54c089c52e1a0753`.
- Modern `SignalProtocolStore` combines identity, pre-key, signed-pre-key, Kyber pre-key, session, and sender-key stores. Its callbacks are synchronous and require durable-copy semantics: loading returns a copy, mutations take effect only after an explicit store call.
- Kotlin therefore cannot implement `SignalProtocolStore` by asynchronously calling back into the existing JavaScript `WorkspaceSession`. The Spike needs a native-side synchronous store with an isolated, documented encrypted persistence boundary; only redacted commands/results should cross Expo Modules.
- Identity trust is explicit TOFU: a new/unchanged identity can be trusted, while replacement is observable and must map to a fail-closed M2Y state until re-verification. The upstream `IdentityChange.REPLACED_EXISTING` contract can later drive safety-number-change UX.
- The existing workspace database is opened asynchronously by Expo SQLite and keyed from a SecureStore value held briefly in the TypeScript secure-workspace controller. It cannot directly satisfy libsignal's synchronous native store callbacks without exposing protocol records over the JS bridge.
- Expo SDK 56 currently resolves Kotlin 2.1.20, while libsignal v0.101.0 declares Kotlin stdlib 2.2.20 plus coroutines/serialization 1.10.x. A minimal compile/runtime compatibility probe must be the first implementation gate; do not design the full store before it passes.
- The generated Android toolchain is compile/target SDK 36, min SDK 24, NDK 27.1.12297006, Hermes, and New Architecture. These match the project's current validated device matrix but do not by themselves prove the newer Kotlin dependency is compatible.
- Expo SQLite compiles its own vendored SQLCipher directly into `libexpo-sqlite.so`; it does not expose a reusable synchronous Kotlin store API. Adding another SQLCipher stack during the Spike would introduce unnecessary native/package risk.
- Android Keystore supports AES keys restricted to GCM/no-padding from API 23, below M2Y's min SDK 24. Android's `AtomicFile` provides crash-safe replace semantics but no locking, so all Spike operations must run through one serialized native executor. Sources: https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec and https://developer.android.com/reference/android/util/AtomicFile.html
- AndroidX `EncryptedFile` is deprecated in security-crypto 1.1.0, so the Spike should not add it. Use the platform Keystore + `Cipher` and `AtomicFile` directly, with OS-generated GCM IVs and a versioned file envelope.
- Recommended Spike-only persistence: operate on a copy of an in-memory `SignalProtocolStore`, checkpoint the complete serialized record set as one Keystore-encrypted atomic file, and expose a result only after checkpoint success. On failure, discard the working copy so ratchet/pre-key state cannot advance without durable commit.
- This checkpoint store is intentionally a feasibility harness, not the production sync/database design. No identity, session record, key, plaintext, or encrypted checkpoint blob needs to cross the Expo Modules bridge; JavaScript receives only stable result codes and aggregate timings.
